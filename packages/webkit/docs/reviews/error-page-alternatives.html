Error page: five alternatives

The state/error-page block today shows a faint 404 numeral, a title, one sentence and two buttons, centred in a mostly empty screen. Below are five ways to make it more useful, each based on how strong developer and cloud products build theirs. Every element is a real WebKit component in a variant it has, coloured with the tokens its .vue source uses. Each alternative is drawn twice: desktop (inside the console shell) and phone (375 px).

01

Quiet and traceable

Based on Vercel, Linear, Fastly. The smallest change: same message, no giant numeral, raised into the upper third, with the error code and a copyable request ID under the actions.

Pros

  • Smallest change to the block; same four variants.
  • Every error gets a request ID and time support can trace (Vercel, Railway, Fastly).
  • No more empty void: content sits in the upper third where the eye lands.

Cons

  • Still a dead end: it does not help the user find what they wanted.
  • Plain; the page does not feel like Azion.

WebKit pieces

  • EmptyState (title, description, actions), StatusCode 404 (warning), Button primary + outline, CopyButton, Timestamp.
  • New: nothing. Only the block's layout and a requestId prop.
02

Find your way

Based on GitHub (search on the 404), Stripe docs (popular destinations), Supabase (one calm way back). The 404 becomes navigation: search the console, or jump to the four places people go most.

Pros

  • Turns a dead end into a next step; fills the empty space with something useful.
  • Search opens the existing Command palette, so ⌘K works the same as everywhere.
  • Keeps the Azion 404 art, smaller.

Cons

  • The app has to pass its destinations (props), and keep them current.
  • Longer on a phone (the list stacks).
  • Makes sense for 404 / 403 / missing resource, less for 500.

WebKit pieces

  • svg/error-404, EmptyState, SearchTrigger + Kbd (opens Command), Item variant outline in an ItemGroup, Button, CopyButton.
  • New: nothing. A destinations prop on the block.
03

Request path

Based on Cloudflare's 5xx pages and Fastly. For errors a visitor of a customer's site sees when Azion cannot reach the origin: shows the hop that failed, what happened, what to do, and the request details.

Pros

  • Answers "whose fault is it?" at a glance; that is what an edge platform's error must say.
  • Fewer support tickets: the site owner learns the origin is down, not Azion.
  • Request ID, edge location and UTC time are what support asks for.

Cons

  • Only for proxy errors (502, 504, origin timeouts); not for the console's 404.
  • It is a different surface (Azion's own error pages served for customer sites), so it would be a new block, not a variant.
  • FlowDiagram is horizontal; on a phone the hops have to stack (drawn here as a vertical list).

WebKit pieces

  • StatusCode 502 (danger), FlowDiagram + nodes, StatusIndicator (success, danger), KeyValueList, CopyButton, Timestamp, Button.
  • New: a new block state/edge-error-page; FlowDiagram would need a vertical layout for phones.
04

Developer details

Based on Railway (JSON body with request_id), Stripe (error object with doc_url) and Vercel (an error code with its own docs page). For a 500 in the console: plain-words message on top, the raw error response below, one click to copy it all.

Pros

  • Developers get exactly what support needs, in one copy.
  • A link to the matching request in Real-Time Events closes the loop.
  • Error codes link to a docs page each (Vercel pattern).

Cons

  • Intimidating for non-developer users (billing, account owners).
  • The API must expose a curated error body; never a stack trace.
  • Needs docs pages per error code to be worth it.

WebKit pieces

  • StatusCode 500 (danger), EmptyState icon tile, Button primary + outline + link, CodeBlock (JSON, with its copy button).
  • New: nothing in WebKit; an error-code docs section on the product side.
05

Split with live status

Based on GitHub (status link on the unicorn page), Google Cloud (Service Health), Netlify and Render (calm copy). The message on the left; on the right a card with the live health of the services, so the user knows at once whether it is them or us.

Pros

  • During an incident, users stop retrying and stop opening tickets.
  • Uses the full width on desktop; stacks cleanly on a phone.

Cons

  • Needs a live status feed; a stale "Operational" next to an error is worse than nothing.
  • Only meaningful for 5xx; a 404 has nothing to do with service health.

WebKit pieces

  • StatusCode 503 (danger), Button, Card with header and footer, StatusIndicator (success, warning), Timestamp, CopyButton.
  • New: nothing in WebKit; a status feed in the app.

Recommendation

Keep one block and give each error the layout that helps most. In plain words: a missing page should help you find the right page; a broken server should tell you it is not your fault and give support what it needs.

  1. Every variant gets the reference line from 01 (error code, request ID with copy, UTC time). Cheap, and it is what support asks for first.
  2. 404, 403 and missing resource use 02, Find your way. Search plus four popular destinations instead of the empty void. Nothing new in WebKit, only a destinations prop.
  3. 500 keeps today's Retry + System status, and adds a collapsed "Details" with the JSON from 04 once the API returns a curated error body.
  4. 03, Request path, becomes its own block later (state/edge-error-page) for the pages Azion serves to visitors of customer sites. It is the strongest idea here, but it is a different surface from the console.
  5. 05 waits until a reliable status feed exists.

Owner to pick: go with this mix, or choose one alternative for every variant.
