Error pages: three options

The owner asked for one consistent style across every common error, not one page. Each option below is a single visual style applied to the same six pages: 404 not found, 401 sign-in required, 403 no access, 429 too many requests, 500 server error and 503 maintenance. Every page is shown on desktop (inside the console shell) and on a 375 px phone. Everything drawn is a real WebKit component in a variant it has, with the colour tokens its source uses; the only orange is the logo orange (--primary).

Decision (owner, 2026-11-18)

Error pages are blocks (copyable screens built from existing components), not a component: Cloudscape, Atlassian, Polaris and Primer document error pages as page patterns, and Cloudflare, Fastly and Vercel serve theirs as hosted templates. They split into two families by who reads them.

  1. Edge, for the visitors of your customers' sites — state/edge-error-page (surface edge). Option 3's diagnostic format on a standalone page: the code and reason, a plain title, the request path You → Azion → Application drawn with TopologyDiagram node cards of one width and height, each with its status tag (side by side on a wide screen, stacked with orientation="vertical" on a phone), What happened? / What can I do?, Try again or Go to home page with Go back, and the request ID, time, Azion location and host. The docs call the middle hop Azion's infrastructure and the page says just Azion; the third hop is the Application, because the site's application may run on Azion's distributed infrastructure or on the customer's own servers (RV-Z1 to RV-Z3). Never an account action. States: 502 (primary), 504, 500, 503, 403 (the site's firewall), 429, 404.
  2. Azion's console, site and docs — state/error-page (surface app). Option 1's quiet, centred style with the existing StatusCode as the figure, a title, one sentence, at most two buttons and the line with the error code, the copyable request ID and the time. States: 404 (primary), 401, 403, 429, 500, 503 and a missing record.

See them on the docs site under Blocks › State › EdgeErrorPage and Blocks › State › ErrorPage. The options below are kept as the record of what was compared (decisions RV-D1, RV-R1 to RV-R3, RV-Z1 to RV-Z3).

OPTION 1

Quiet and traceable

Based on Vercel, Linear, Supabase and Fastly. One short centred column in the upper third: the HTTP code as a StatusCode pill, a title in plain words, one sentence, up to two actions, and a reference line (error code, request ID with copy, UTC time) on every page. Only the words and the actions change from page to page.

Pros

  • Smallest change from today; one layout for every error, easy to keep consistent.
  • Every page carries the request ID and time support asks for.
  • Calm; reads well on a phone.

Cons

  • A 404 is still a dead end (no search, no destinations).
  • A 429 or 503 says when to come back only in words.
  • Plain; little that says Azion.

Reused vs new

  • Reused: EmptyState (title, description, actions), StatusCode, Button primary + outline, CopyButton, Timestamp.
  • New: no component. The block gets code and requestId props and three new variants (401, 429, 503).
OPTION 2

Guided recovery

Based on GitHub (search on the 404), Stripe (popular destinations), Google Drive (Request access, Switch account, signed in as) and status pages with a maintenance window. The same centred style, with the 404 / 403 numeral art or the EmptyState icon tile, and under the message one panel built for that reason: search and destinations, who you are signed in as, a wait meter, a maintenance window.

Pros

  • Every page gives a real next step, not only "go home".
  • 403 and 401 name the account, the most common cause of both.
  • 429 and 503 show when to come back; Retry is disabled until then.

Cons

  • The app must pass data: destinations, the signed-in account, the admin, the reset time, the maintenance window.
  • Six different panels to keep consistent.
  • Longer pages on a phone.

Reused vs new

  • Reused: EmptyState, svg/error-404, svg/error-403, SearchTrigger + Kbd (opens Command), Item outline, Avatar, Alert info, Progress, Button (incl. disabled), Timestamp, CopyButton.
  • New: no component. New 401, 429 and 503 variants and props for the data above.
OPTION 3

Diagnostic

Based on Cloudflare (which hop failed; What happened / What can I do; Ray ID), Railway and Stripe (request ID, error object), GitHub API (limit, remaining, reset). Left-aligned, the method and code as one StatusCode pill next to a machine-readable error code, two columns that separate what happened from what to do, the actions, then the request facts in a KeyValueList. Server errors show the request path.

Pros

  • Answers "whose fault is it, and what do I do?" on every page, the way an edge platform should.
  • The facts support needs (request ID, path, time, limit, Retry-After) are always in the same place.
  • The same style works for Azion's own pages served to visitors of customer sites.

Cons

  • Technical; heavier for non-developer users (billing, account owners).
  • Machine error codes must exist and be documented.
  • The request path diagram does not fit a phone, so it is left out there.

Reused vs new

  • Reused: StatusCode (method + code), Button, KeyValueList 4 columns, CopyButton, Timestamp, FlowDiagram + nodes, StatusIndicator.
  • New: no component. New block variants; a docs page per error code on the product side.

Recommendation

Go with Option 2, Guided recovery, and add Option 1's reference line (code, request ID, time) to every page of it.

  1. Why 2: it is the only option where every error page gives a real next step: search on a 404, the signed-in account on 401 and 403, a wait meter on 429, the maintenance window on 503. It keeps the look the console already has (EmptyState, the Azion 404 and 403 art) and needs no new component.
  2. Why not 1: consistent and cheap, but the 404 stays a dead end, which is what the owner disliked in today's page.
  3. Why not 3 for the console: too technical for people who manage billing or teams. Keep it for later as the style of the error pages Azion serves to visitors of customer sites (502, 504, application timeouts), where "whose fault is it" matters most.
  4. What it costs: three new block variants (401, 429, 503) and props for the data each panel needs; the existing 404, 403, 500 and missing-resource variants are reworked in the same style.

Decided: Option 3 for the edge pages, Option 1 for the console, site and docs (see Decision at the top).
