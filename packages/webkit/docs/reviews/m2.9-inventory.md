# M2.9 inventory: the design sample, the Console Kit and Cloudscape against WebKit

Phase 1 of M2.9 (2026-11-11). This file lists every piece the products use that WebKit does not have
yet, or has in a different design. For each piece it gives the source, where it is used, the WebKit
equivalent, what it becomes and its size. It then groups the work into packages that agents can
build in parallel. The sources are taken in this order, and the order settles every conflict:

1. **The design sample** (`apps/webkit-sample` on the `design/sample` branch, 1,179 files). **Its design always wins.**
2. **The Console Kit** (`aziontech/azion-console-kit`, read-only clone at `$S/console-kit`, commit
   `50f676d`), used only for what the sample does not have.
3. **Cloudscape's component list**, used only for what neither of the first two has.

Generative AI pieces (chat, prompt input, suggestions, the docked assistant) belong to the M2.4
lane. They are marked **M2.4** below and are not packaged here.

**How to read the tables.**

- **Decision** is one of:
  - **component**: a new export in `src/components`, built through the M1.3 spec-first flow.
  - **block**: a new screen in `blocks/`, or a new variant of an existing block.
  - **pattern**: rules and guidelines in a skill or a block's `guidelines.md`, with no new export.
  - **product**: stays product code. A product screen keeps its data and wiring, and WebKit only
    supplies the parts it is made of.
- **Done** means WebKit already has the piece. The equivalent column names it.
- **Size:** S is under a day for one agent, M is one to two days, L is three days or more.
- **WP** is the work package (see the end of this file).
- Sample paths are relative to `apps/webkit-sample/src/` and Console Kit paths to `src/`.

**Naming convention kept.** WebKit blocks use fictional, product-neutral data. For example, the
sample's Connector, Application and Rules Engine appear in blocks as origin, service and routing
rules. That convention came in with M1.1 and does not change here. "The sample's design wins" means
the layout, the states, the surfaces, the placement of messages and actions, and the behaviour. It
does not mean the demo data.

The `color-contrast` findings are almost all in the light theme (150 files, against 8 in dark), and most are marketing sections and site examples. The first step is to read the failing pairs from one run with `VITE_A11Y_RECORD` unset. If they share a token pair (muted or secondary text on a raised or tinted surface), the fix is one token change in light mode rather than one per file. The structural rules are the same in every pass, so they come from the components and not from the theme: `aria-required-children` and `aria-required-parent` (lists, tabs, menus and grids whose children lack the role), `button-name` (icon-only buttons with no name), `link-in-text-block`, `aria-progressbar-name`, `nested-interactive` and `label`. One fix per component clears every example that uses it.

Beyond what axe can see:

- **Keyboard maps.** Every overlay (`Dialog`, `Drawer`, `Popover`, `DropdownMenu`, `Select`,
  `MultiSelect`, `Command`, `Tooltip`) has a keyboard test of its documented map: open, move, select,
  Escape, and focus returning to the trigger. The tests exist for most of them. The package adds the
  missing ones and makes the spec's keyboard section the source of each test.
- **Live regions.** Toasts, `StatusIndicator`, async results (`async-submit`), and the form-error
  `Alert` are announced once and politely. The package adds an assertion that each one sits in, or
  is, a live region, and that streaming `LogView` lines do not each announce.
- **Forced colors.** Focus rings, selected states, the switch thumb, chart marks and the
  `StatusIndicator` dot must stay visible with `forced-colors: active`. Axe cannot check this, so the
  package adds a screenshot pass per component in the visual suite under forced colors.
- **Reduced motion.** The media pass flags infinite animations. The package also checks that
  entrance animations (`animate-page-enter`, popup scale) are removed under reduced motion.
- **Screen reader smoke.** One scripted pass per overlay and per form block with the
  accessibility tree snapshot (`page.accessibility.snapshot()` through a browser command), checked
  into the test as an inline snapshot.
- **Contrast of muted labels.** The StatusIndicator loading label (`--text-muted`) and every
  `--text-muted` on `--bg-surface-raised` pair in dark mode get checked against 4.5:1.

## 6. Removing the sample's structure

`apps/webkit-sample` lives on the `design/sample` branch, not on `feat/webkit-ai-ready`. Removing it
means retiring that app once WebKit can render everything it renders. It goes only when every box
below is checked.

**What must exist in WebKit first:**

- Every row above whose decision is a component or a block is done, which means every package in
  section 4 except `a11y`, which can continue after the removal.
- Every console page of the sample (126 files in `console/pages`) renders from WebKit blocks and
  components, with only product data and wiring left in the page.
- Every site landing (60 views) and docs page renders from WebKit sections, `Doc*` components and
  `shells/website` or `shells/documentation`.
- The hub's foundations pages have a home in the docs site (M2.5).
- `preview/` decks and `lab/` sandboxes are product tooling. They are not ported. They are archived
  with the branch, and the archive is recorded in the roadmap.

**Compatibility checklist:**

- [ ] **Visual parity.** Each sample route is rendered twice, once from the sample and once from
      the WebKit composition, at three widths and in both themes, and compared with the Storybook visual
      suite. Differences are either fixed or written down as design decisions.
- [ ] **Marketing inventory.** Every site section, asset, figure and scene that leaves the sample
      has a record in `packages/webkit/scripts/marketing-inventory.json` (`items`, or `renamed` and
      `removed`), and `node scripts/check-marketing-inventory.mjs` passes.
- [ ] **Behaviour.** The sample's `lib/behavior` modules that encode UX rules (`reveal-invalid`,
      `forms.js` `useBaseline`, `tab-dirty`, `anchor-nav`, `list-morph`, `drag-reorder`,
      `variables-editor`, `project-upload`, `version-commit`) each map to a WebKit composable, component
      feature or skill rule, as listed in the tables.
- [ ] **Deploy state.** `console/lib/state/deploy-runs.js` is reproduced by the async-submit
      pattern (a module-scope run store, one toast id per run, Edit and Redeploy).
- [ ] **Skills and rules.** The sample's `.claude/skills` and `.claude/rules` are symbolic links into
      this repository, so they need no move. Delete them with the app.
- [ ] **Preview deploy.** `azion/`, `azion-preview/` and `scripts/deploy-preview.sh` are replaced
      by the docs site deploy (M2.5).
